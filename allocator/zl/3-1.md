### 4. **高效节点管理(3.3.4)**

#### alloc_node实现（带注释代码）
```rust
pub fn alloc_node(&mut self) -> Option<usize> {
    // 1. 检查空闲链表
    let node_addr = self.free_head?;
    // 2. 从链表头部取出节点
    let node = unsafe { &mut *(node_addr as *mut ListNode) };
    self.free_head = node.next;
    node.next = None;
    // 3. 更新统计
    self.total_allocations += 1;
    self.free_nodes -= 1;
    // 4. 返回节点地址
    Some(node_addr)
}
```
- **性能特性**：O(1)、无内存分配、缓存友好

#### dealloc_node实现
```rust
pub fn dealloc_node(&mut self, node_idx: usize) {
    // 1. 清空节点数据
    unsafe { core::ptr::write(...) };
    // 2. 更新链表头
    self.free_head = Some(node_idx);
    // 3. 更新统计
    self.total_deallocations += 1;
    self.free_nodes += 1;
}
```
- **性能特性**：O(1)、插入链表头部、清零防信息泄漏

#### get_node访问接口
- 只读访问：`get_node`
- 可变访问：`get_node_mut`
- 用途：free list遍历、节点数据读写、链表指针修改

#### 统一节点管理接口图

### 本发明要解决的技术问题

在现有实现中，本项目的内存分配器采用“每个 block 开头预留若干字节作为 header”的元数据管理方式，并结合伙伴算法按阶(order)维护空闲块链表。该方案在单一内存类型、单一安全域的简单场景下能够较好地工作，但当其部署在 Type-I Hypervisor、异构内存系统以及多 zone、大规模内存环境时，逐渐暴露出如下技术问题:

1. 元数据与被管理物理内存深度耦合，缺乏安全隔离能力  
   现有 header 方案要求在 free 状态下直接在物理页开头写入 allocator 的链表指针等元数据，这些页未来将被分配给 guest 或不同安全域使用。对于 Type-I Hypervisor、多信任域系统等场景，guest 侧的越界写、use-after-free、DMA 攻击等错误或恶意行为，都有可能在 free 状态下破坏这些 header，从而损坏内存分配器的核心数据结构，导致页框泄漏、内存破坏等严重后果。现有实现缺乏将 allocator 元数据与被管理物理内存彻底隔离的机制。

2. 多 zone 场景下节点资源分散，利用率低且管理复杂  
   在支持多内存区域(zone)的场景下，现有实现通常需要为每个 zone 预留一定量的 header 或隐含的“节点容量”。当不同 zone 的负载不均衡时，某些 zone 的 free block 及其 header 资源长期闲置，而另一些热点 zone 可能频繁接近“节点不足”的极限。节点/元数据资源无法在 zone 之间流动，共享程度低，导致整体内存利用率下降，同时也使得多 zone 管理逻辑更为复杂，新增或移除 zone 时容易引入错误。

3. 面向异构与远端内存时，元数据访问开销大且不易控制  
   在引入 NUMA 远端内存、CXL 扩展内存、设备内存/MMIO 映射区域等异构资源时，现有 header 方案要求在这些“慢速”或“访问受限”的内存上直接读写 header。每次 free/alloc 操作都可能触发跨 NUMA、跨总线访问，带来显著延迟；对某些设备内存/持久内存(PMEM)，频繁写入 header 还会引入额外的写放大和寿命损耗。现有实现难以将“元数据读写路径”限制在一块高性能、受控的内存区域中，无法独立优化不同内存类型上的访问行为。


因此，本发明提出一种面向 Type-I Hypervisor 和异构内存环境的“全局动态扩展节点池”机制，在保持现有伙伴算法整体架构的基础上，通过将链表节点集中存放在一个可独立调控、可跨 zone 共享的全局节点池中，实现 allocator 元数据与被管理物理内存的彻底隔离，显著提升多 zone/多内存类型场景下的元数据利用效率与访问性能，并为系统提供可配置的水位扩展策略和集中化观测能力，以解决上述至少一种技术问题。

## 1. 元数据与被管理物理内存深度耦合 → 要做什么

目标：  
- 元数据完全放在“全局节点池的专用区域”里；  
- 这个区域**不**作为任何 zone 的一部分；  
- 上层 Hypervisor 能拿到这块区域做单独映射（只给 hypervisor，看不到 guest）。

你现在的 `allocator/src/buddy/buddy_allocator.rs` 其实已经做了**一半**：

```rust
// 关键片段
let node_region_size = NODE_POOL_PAGES * PAGE_SIZE;
let node_region_start = base_addr;

self.global_node_pool
    .init(node_region_start, node_region_size);

let zone_base = base_addr + node_region_size;
let zone_size = size - node_region_size;

self.zones[0] = BuddySet::new(zone_base, zone_size, 0);
self.zones[0].init(&mut self.global_node_pool, zone_base, zone_size);
```

这里已经保证了“节点池区域不进任何 zone”。  
为了真正支撑 3-1.md 第 1 点，你需要额外**补一条能力**：把节点池区域暴露给上层用来做 MMU 权限配置。

### 建议新增接口：导出节点池物理区间

## 2. 多 zone 场景下节点资源分散 → 要做什么

- `BuddySet` 里：每个 zone 的 free list 都是 `PooledLinkedList`，节点来自同一个 `GlobalNodePool`：

```rust
pub struct BuddySet<...> {
    ...
    /// Free lists for each order

## 3. 异构 / 远端内存上元数据访问开销大 → 要做什么

这一条要支撑好，需要两个层面的设计：

1. **保证元数据始终在“快速内存”上**  
   这一点你现在的实现已经天然满足：节点池区域是用 bootstrap 的首段内存（通常是本地/普通内存）建出来的，free list 操作只动 `GlobalNodePool`，不会去访问被管理的块内容，不存在 header 落在 CXL/远端/PMEM 上的问题。

2. **让 allocator 能区分不同类型的 zone，并根据类型做策略选择**  
   这部分目前只有 `is_lowmem`（<4G DMA32）一个维度，还缺“普通/远端/设备/持久内存”等类型描述，以及相应的 API。

        alignment: usize,
        kind: MemoryKind,
    ) -> AllocResult<usize> {
        self.maybe_expand_node_pool();

        for i in 0..self.num_zones {
            if self.zones[i].mem_kind != kind {
                continue;
            }
            if let Ok(addr) = self.zones[i].alloc_pages(&mut self.global_node_pool, num_pages, alignment) {
                #[cfg(feature = "tracking")]
                self.update_stats();
                return Ok(addr);
            }
        }

        Err(AllocError::NoMemory)
    }
}
```

上层就可以做到：

- GPU 显存：先用 `add_memory_region_with_kind(..., MemoryKind::Device)` 注册；  
  分配显存相关页时，调用 `alloc_pages_in_kind(..., MemoryKind::Device)`。  

- CXL：`MemoryKind::Cxl`；  
- PMEM：`MemoryKind::Pmem`，业务逻辑可以根据 types 做不同策略（比如写入更谨慎）。

**关键点：**  
由于 free list 的元数据已经集中在 `GlobalNodePool` 的“快速内存”上，上述 MemoryKind 区分只影响“实际业务页”在哪个 zone 上分配，不会改变元数据读写永远走快内存这一事实，从而实现 3-1.md 第 3 点说的“把元数据读写路径锁死在一块高性能、受控的内存区域中”。

- 为解决 **问题 1（安全隔离）**：在现有全局节点池实现上，新增“节点池专用 region 记录 + 对外查询接口”，让上层能单独配置 MMU 权限。  
- 为解决 **问题 2（多 zone 节点资源分散）**：现有全局节点池 + pooled list 已经实现跨 zone 共享，只需按需补充 per-zone 节点使用统计接口，主要是文档上把“单池多 zone”写清楚。

### 附加说明：本发明要解决的问题及全局节点池方案的必要性

从工程实践看，buddy 分配器常见的链表实现方式主要有两种：在每个空闲 block 开头预留若干字节作为 header和为每个 zone 单独维护固定大小、彼此独立的节点池。这两种方案在“单机、单一内存类型、单一安全域”的简单场景下都能正常工作，但一旦放到本项目目标的实际环境中——例如 Type-I Hypervisor、多 zone 管理、以及存在多种“速度和用途不同”的内存（例如本地内存、远端 NUMA 内存、通过总线扩展的内存、设备专用内存等）——就会暴露出一些难以同时满足的要求：

1. **安全性要求：元数据不能暴露给不可信客体**  
   在 header 方案里，free 状态下的物理页开头存放的是分配器的内部链表指针。将来这些物理页会被分配给不同的 guest 或不同安全级别的组件使用，一旦出现越界访问、use-after-free、恶意 DMA 等行为，就有可能在“分配器还没看到”的情况下把这些 header 改写掉，直接破坏 allocator 的核心结构。  
   对于 Type-I Hypervisor 来说，我们希望有一种机制：分配器的元数据全部放在一块只有 Hypervisor 自己能访问的内存里，guest 无法直接读写，从根上降低被破坏的风险。传统 header 写在 block 里的做法，很难满足这一点。

2. **多 zone 利用率要求：节点资源不能被某个 zone 长期“锁死”**  
   在每个 zone 各自预留固定节点池的方案里，节点资源被预先“切块”分给了不同 zone。  
   - 某些 zone 可能长时间比较空闲，它的节点池几乎不用；  
   - 另一些热点 zone 则可能频繁分配/回收，节点池容易打满或接近极限。  
   结果是：系统层面明明还有不少节点“闲着不用”，却因为被锁在其他 zone 里，忙的 zone 用不上。这样既浪费内存，又增加了多 zone 管理的复杂度。我们希望的是：所有 zone 在需要链表节点时，都能从同一个“公共池子”里拿，哪里忙就把资源用到哪里。

3. **不同类型、不同速度内存的性能要求：慢内存上尽量少做“频繁的小操作”**  
   在现代系统里，内存并不都是一样的：  
   - 有的在本地 CPU 插槽附近，访问很快；  
   - 有的在远端 NUMA 节点上，通过互联总线访问，延迟更高；  
   - 还有的可能是通过 CXL 之类的总线扩展上来的大容量内存，或者是设备专用内存、持久内存等。  
   如果采用 header 方案，把每次 free/alloc 都需要读写的链表指针等元数据直接放在这些“远一些、慢一些”的内存上，那么每一次页框回收、再次分配都会触发一次慢访问，整体性能很难控制。甚至对于某些需要减少写入次数的介质（比如持久内存），频繁更新 header 还会带来额外的写放大和寿命压力。理想的做法是：**频繁读写的元数据集中放在一小块高性能、受控的内存中，真正的业务数据才放在这些不同类型的内存上**。

综合来看，传统的“block header”方案和“按 zone 固定节点池”方案，很难同时满足：
- Hypervisor 级别的安全隔离要求（元数据不暴露给 guest）；
- 多 zone 场景下的节点资源弹性共享；
- 针对不同类型、不同速度内存的访问路径优化。

为了解决这些问题，本发明提出并采用**全局动态扩展节点池**方案，其核心思路可以用几句话概括：

1. **把元数据集中放到一块专用的全局节点池内存区域**  
   这块区域不属于任何一个 zone，只由 Hypervisor 映射和访问。所有 free list 链表节点都放在这里，guest 使用的物理页内部不再写入 allocator 的指针或控制字段，从物理上把“数据”和“元数据”隔离开。

2. **所有 zone 共享同一个节点池，节点可以按需在各个 zone 之间“流动”**  
   不再为每个 zone 固定预留节点数量，而是依据当前负载动态地从全局节点池中申请和释放节点。哪一个 zone 瞬时比较忙，就自然地多用一些节点；哪一个 zone 空闲，就少用一些，避免资源浪费。

3. **将高频访问的元数据固定在本地快速内存中，慢内存只存放业务数据**  
   节点池可以优先放在本地、延迟低的内存区域；而本来“速度较慢”的远端内存、大容量扩展内存等，则主要承载用户数据本身。这样 free/alloc 过程中大量的小型链表操作都发生在快内存里，对慢内存的访问次数被显著减少。

在当前实现的基础上，本发明的方案并不要求推翻现有的伙伴算法框架，而是**替换“元数据放在 block 开头”这一点**：  
把原来存放在 block header 里的链表指针、阶数等信息，改为通过全局节点池申请和管理的节点结构来承载。这样，既保留了现有 buddy 分配/合并逻辑的整体结构，又天然获得了上面提到的安全隔离、跨 zone 共享以及对多种内存类型更加友好的访问特性，这正是本发明要解决的核心技术问题所在。


2. **所有 zone 共享同一个节点池，节点可以按需在各个 zone 之间“流动”**  
   不再为每个 zone 单独固定预留节点数量，而是把不同地址区间（无论是物理地址还是虚拟地址划分出来的内存区域）统一看作多个 zone，由它们共同使用同一个全局节点池。哪一个 zone 在某个时刻比较忙，就自然地多用一些节点；哪一个 zone 相对空闲，就少用一些节点，从而避免节点资源被某个 zone 长期锁死而无法被其他 zone 利用。

   内存区域（zone）管理：为适应不同用途或属性的内存，以及处理地址空间中的不连续区间，系统可以将可管理的地址空间划分为多个“内存区域”（zone）。每个 zone 对应一段连续的地址区间（可以是虚拟地址区间，在具体实现中通常再映射到不同的物理内存范围，如低地址内存、高地址内存、设备映射内存等），由内存分配器分别维护，从而在逻辑上对不同区域进行差异化管理。
