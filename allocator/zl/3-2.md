```markdown
### 4 系统整体架构

#### 4.1 架构总体概述

本发明面向 Type-I Hypervisor 场景，提供了一套基于伙伴算法的多区间内存管理架构。系统将可管理的地址空间划分为若干个逻辑上的内存区域（zone），每个 zone 对应一段连续的虚拟地址区间，由伙伴分配器进行块划分和回收；所有 zone 在维护空闲块链表时，共享同一个全局动态扩展节点池，由节点池统一提供链表节点等元数据存储空间。

在这一架构下：

- 业务数据（即将来分配给各个虚拟机或内核模块使用的页框内容）始终位于各个 zone 的虚拟地址区间中；
- 分配器内部使用的元数据（空闲块链表节点等）集中存放在一块独立的全局节点池地址区域内，与业务数据所在的各个 zone 相互隔离；
- 上层组件通过统一的接口向伙伴分配器申请和释放内存，由分配器在多个 zone 之间选择合适的地址区间完成分配，同时通过全局节点池维护各个 zone 的空闲状态。

整体目标是：在不改变伙伴算法基本思想的前提下，通过引入“全局节点池 + 多 zone 管理”的架构，将元数据集中化、共享化、可控化，从而提升安全性、资源利用率和对复杂内存环境的适应能力。

#### 4.2 主要模块与职责划分

系统整体可以划分为三层：上层使用接口层、核心内存管理层以及元数据存储层，各层之间的关系如下所示：

- 上层使用接口层：向 Hypervisor 其它组件（如虚拟机管理、内核子系统）提供统一的内存申请与释放接口；
- 核心内存管理层：由多 zone 管理、伙伴算法和策略决策逻辑组成，负责决定在哪个 zone、以多大粒度进行分配和回收；
- 元数据存储层：由全局动态扩展节点池构成，专门负责存放空闲块链表节点等元数据，并为核心层提供统一的节点申请与释放能力。

从模块角度可以进一步拆分为以下几个核心组成部分：

1. **Zone 管理子系统**  
   - 管理多个不连续的虚拟地址区间，每个区间抽象为一个 zone；  
   - 记录每个 zone 的起始地址、长度以及与之关联的伙伴集合（Buddy 集合）；  
   - 支持在系统运行过程中注册新的地址区间或标记某些区间不可用，为 Hypervisor 动态调整内存布局提供基础。

2. **Buddy 集合（BuddySet）与空闲链表管理**  
   - 每个 zone 内部使用伙伴算法按阶（order）划分内存块，并为每个阶维护一条空闲块链表；  
   - 空闲链表使用从全局节点池分配的节点来串联，节点中仅存储块的地址和阶等必要信息，实际数据仍在 zone 的虚拟地址区间中；  
   - 在分配、合并、拆分等操作过程中，通过节点池提供的接口高效获取和归还链表节点。

3. **全局动态扩展节点池（Global Node Pool）**  
   - 节点池占用一段独立的地址区间，不属于任何一个具体 zone，只由 Hypervisor 自身访问；  
   - 向所有 zone 的伙伴集合统一提供“分配链表节点”和“回收链表节点”的能力；  
   - 内部维护空闲节点链表及统计信息，根据运行时的节点使用情况自动触发扩展，在需要时从系统可用内存中再划出一小段空间用于增加节点数量；  
   - 通过这一集中式设计，保证元数据存放位置恒定可控，方便单独配置访问权限和保护策略。

4. **策略与监控子系统**  
   - 根据系统配置和运行时状态，决定在多个 zone 间如何选择分配目标（例如优先选择某些 zone，或进行简单的负载均衡）；  
   - 对全局节点池的空闲节点数进行水位监控，低于阈值时主动触发扩展逻辑；  
   - 提供节点池和各个 zone 的使用统计数据，为运维和性能调优提供依据。

#### 4.3 模块之间的关系与数据流

从整体关系来看，各模块之间的连接可以概括为：

- 上层组件只与“内存管理接口”交互，提出“申请一定大小内存”或“归还一段内存”的请求；
- 内存管理接口根据请求大小、zone 策略等信息，选定一个 zone 及其内部的某个 order，调用对应的 Buddy 集合进行分配或回收；
- Buddy 集合在维护空闲链表时，并不自行分配节点，而是通过全局节点池申请或释放链表节点；
- 全局节点池负责记录空闲节点、已用节点的整体情况，根据水位策略在必要时从系统可用内存中扩展自身容量。

可以用简化示意图表示为：

```
上层组件/虚拟机管理
        │
        ▼
  内存管理接口层
        │
        ▼
  ┌───────────────┐
  │  多 zone 管理  │
  │ (多个虚拟地址区间) │
  └───────────────┘
        │
        ▼
  ┌───────────────┐
  │   Buddy 集合   │
  │ (每个 zone 一组)│
  └───────────────┘
        │   ▲
   需要节点 │   │ 释放节点
        ▼   │
  ┌────────────────┐
  │ 全局动态扩展节点池 │

```
在这一数据流中，业务数据始终停留在各个 zone 的虚拟地址区间中，只有极少量描述这些数据块的元数据（链表节点）进入全局节点池，从而在逻辑上形成“业务数据在 zone，元数据在池”的清晰分层。

#### 4.4 典型工作流程概述

1. **系统启动与初始化流程**  
   - Hypervisor 启动后，首先预留一小段地址区间作为全局节点池的初始空间，并完成节点池的初始化；  
   - 随后，将可管理的虚拟地址区间按需要划分为若干个 zone，分别构建对应的 Buddy 集合，并使用节点池提供的节点初始化各阶的空闲链表；  
   - 初始化完成后，整个系统进入“多 zone + 全局节点池”协同管理状态。

2. **内存分配流程（简要）**  
   - 上层组件发出内存申请请求；  
   - 内存管理接口根据请求大小和策略选择合适的 zone 和 order；  
   - 选定的 Buddy 集合从对应阶的空闲链表中取出一个空闲块，同时使用从全局节点池获取的节点维护链表结构；  
   - 返回对应虚拟地址，映射到底层物理资源后供上层使用。

3. **内存回收与节点回收流程（简要）**  
   - 上层组件归还一段先前分配的内存；  
   - 内存管理接口定位到对应的 zone 和 Buddy 集合，执行伙伴合并逻辑；  
   - 在重建空闲链表时，按需要向全局节点池归还或申请新的链表节点，确保节点池中的节点数量与当前 free 块数量相匹配。

4. **节点池动态扩展流程（简要）**  
   - 在系统运行过程中，节点池持续进行空闲节点计数和水位检测；  
   - 当空闲节点数低于预设阈值时，触发扩展流程，从系统尚未使用的虚拟地址区间中划出一小段空间，初始化为新的节点块并加入节点池；  
   - 扩展完成后，节点池无需感知具体 zone 的内部情况，即可为所有 zone 提供更多的链表节点。

通过上述整体架构设计，本发明在逻辑上实现了“多虚拟地址区间统一管理 + 元数据集中存放 + 节点资源跨 zone 共享”的一体化方案，为 Type-I Hypervisor 及复杂内存环境下的安全、高效内存管理提供了一个清晰、可扩展的架构基础。
```

#### 3.3.1 全局节点池结构设计

##### 3.3.1.1 核心数据结构

全局节点池（GlobalNodePool）是专门用于存放链表节点的内存池，所有 zone（即多个不连续的虚拟地址区间）以及各个阶（order）在维护空闲块链表时，共享同一节点池。

**链表节点结构（逻辑定义）**  

每个链表节点用于描述一个空闲内存块，并将其串接到对应阶的空闲链表中，至少包含以下信息：

- **块信息字段**：记录该空闲块的核心属性，例如所在地址区间中的起始地址、所在阶（order）等，用于伙伴算法执行合并、拆分和查找操作；
- **链接字段**：用于指向同一条空闲链表中的下一个节点。实现上通常以整数形式保存下一个节点在节点池中的位置（例如地址或索引），而不是语言层面的引用，以便支持节点池区域的扩展和简单的序列化。

通过这种设计，链表节点本身只承载“描述信息”和“链表链接”，并不包含真实数据页的内容，真实的业务数据始终保留在各个 zone 的虚拟地址区间中。

**全局节点池结构（逻辑定义）**  

全局节点池本身作为一个集中管理的元数据存储区域，主要维护以下状态：

- **空闲节点链表头指针**：指向当前空闲节点链表的第一个节点，用于在分配节点时以常数时间找到可用节点；
- **节点总数计数器**：记录节点池中总共包含的节点数量，用于容量规划和上限控制；
- **空闲节点计数器**：记录当前尚未使用的空闲节点数量，是触发“节点池水位扩展”策略的关键指标；
- **分配与回收统计计数器**：分别统计节点分配次数和回收次数，可用于运行时性能分析、内存泄漏排查以及评估不同负载下的节点使用模式。

**集中管理特性**  

在上述基础上，全局节点池具备如下集中管理特性：

- **空闲节点链表管理**：所有未使用的节点通过链接字段串联成单链表，在典型实现中可以做到分配和回收操作的时间复杂度接近 O(1)，减少节点本身管理带来的额外开销；
- **实时计数与水位监控**：通过节点总数与空闲节点数的组合，系统可以实时评估当前节点池的压力情况，当空闲节点低于预设阈值时，触发动态扩展流程，从系统可用内存中再划出一小段地址区间初始化为新的节点；
- **地址形式链接设计**：节点之间使用整数形式（如地址或偏移量）来表示链接关系，而不是语言层面的引用或指针对象，使得节点池区域的扩展、更换映射方式等操作更为灵活，也避免了与具体编程语言生命周期模型紧耦合的问题。

通过上述数据结构设计，全局节点池在逻辑上为所有 zone 和各阶的空闲块链表统一提供了一个高效、可监控、可扩展的元数据存储基础，为后续的自举初始化、动态扩展策略以及跨 zone 共享提供了支撑。

```markdown
##### 3.3.1.3 节点池与 Buddy 系统的自举与协同关系

在本发明中，全局节点池与 Buddy 系统之间不是简单的“互不相干的两个区域”，而是形成了一个可以自举并支持运行期扩容的闭环关系。

**（1）初始化阶段的自举关系**

系统启动时，Hypervisor 会为内存分配器提供一段连续的虚拟地址区间（记为某个 zone）。在该 zone 内，节点池与 Buddy 管理区域的关系如下：

- 先从这段地址区间的起始部分划出一小段子区间，用于初始化全局节点池；

- 剩余的大部分地址区间则全部交给 Buddy 系统管理，作为将来真正分配给上层组件使用的“用户内存”；  
- 在对剩余区间进行 Buddy 初始化时，需要为各阶空闲块建立 free list，此时所需的链表节点全部从刚刚初始化好的全局节点池中按需获取，从而完成分配器自身的“自举”。

用逻辑示意可表示为：

```

┌──────────────────────────────────────────────┐
│                 Zone 0                      │
├──────────────────────────────────────────────┤

│  ────────────────▲──────────────────────────│
│                  │                           │
│          Buddy 管理子区间 (其余页，用于用户) │
│          在初始化时使用上方节点池提供的节点  │
└──────────────────────────────────────────────┘
```

在这一阶段，节点池负责“先为自己准备好足够的节点”，然后再反过来支撑 Buddy 对整段 zone 的管理，因此可以不依赖外部分配器，完成完全自启动。

**（2）运行阶段的协同与动态扩容**

系统运行一段时间后，随着各个 zone 中 free list 的变化，全局节点池中的空闲节点数可能逐渐下降。为了避免节点枯竭，本发明引入了基于水位线的动态扩容机制：

- 当节点池监测到空闲节点数低于某个阈值时，会向 Buddy 系统申请再划出若干页内存；  
- 这些页仍然来自某个已管理的虚拟地址区间（即某个 zone 的 Buddy 管理子区间），但在划出之后不再用于用户数据，而是被格式化为新的链表节点批次，加入节点池的空闲节点链表；  
- 随着新节点被加入，全局节点池的空闲节点数恢复到安全水位以上，继续为所有 zone 的 free list 提供节点支持。

这一动态关系可抽象为：

```
              申请页用于扩容
    ┌───────────────┐       ┌────────────────────┐
    │   Buddy 系统   │──────▶│ 全局节点池 (Global) │
    │ (管理各个 zone)│       │  将整页格式化为节点 │
    └───────────────┘◀──────└────────────────────┘
             使用节点构建 free list
```

综上，节点池与 Buddy 系统之间形成了一个闭环：

- 起始时，先从原始 zone 中“切出”一小块区域作为节点池，并用这块区域自举出足够的链表节点；
- 之后，Buddy 系统使用这些节点对剩余的大区间进行块管理；
- 当节点池节点不足时，再从 Buddy 管理的区间中按页申请内存来扩充节点池容量。

通过这种设计，分配器可以在不依赖外部内存管理组件的前提下，自主完成启动和后续扩容，同时保持节点池与用户数据所在地址区间的清晰分离。
```
